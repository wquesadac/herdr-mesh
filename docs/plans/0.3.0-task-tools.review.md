# Review of herdr-mesh 0.3.0 Spec (`docs/plans/0.3.0-task-tools.md`)

This review evaluates the 0.3.0 task tools specification against the current codebase (`src/tools/agent.ts`, `src/types.ts`, `src/tools/composite.ts`, `src/server.ts`, `src/herdr.ts`), the real `herdr 0.9.5` CLI behavior, and `@modelcontextprotocol/sdk` v1.29.0.

Findings are classified as:
- **BLOCKER**: Critical defects, incorrect CLI commands/shapes, race conditions, or runtime crashes that will break functionality or tests.
- **SHOULD**: Significant robustness, error-handling, or architectural issues that would cause incorrect guesses or subtle failures.
- **NIT**: Minor ambiguities, non-fatal edge cases, or over-engineered elements.

---

## Summary of Findings

- **BLOCKER**: 6
- **SHOULD**: 9
- **NIT**: 6

## BLOCKER Findings

### 1. [BLOCKER] Section 4 — `herdr worktree create` does not return a pane ID
- **Spec Section**: Section 4 (`herdr_task_run`, lines 100–104)
- **Problem**:
  The spec states:
  > `worktree: { repo: string, branch: string, base?: string, path?: string } — runs herdr worktree create ...; the agent runs in the new worktree's root pane. Check the real output shape of worktree create live, and add a case to extractPaneId if needed;`
  
  In `herdr 0.9.5` (`WorktreeCreated` schema in `herdr api schema --json`), `herdr worktree create` returns `{ type: "worktree_created", workspace: WorkspaceInfo, worktree: WorktreeInfo }`. Unlike `workspace create` (which returns `{ workspace, tab, root_pane }`), `worktree create` returns neither `root_pane` nor `pane_id`. `extractPaneId` cannot extract a pane ID from this response, causing `herdr_task_run` with worktree placement to fail immediately with `"did not return a pane id"`.
- **Concrete Fix**:
  Update Section 4 to specify: after running `herdr worktree create`, extract `workspace_id` from `result.workspace.workspace_id`, then run `herdr pane list --workspace <workspace_id>` to obtain the workspace's root pane ID before calling `startAgent`.

### 2. [BLOCKER] Section 4 — `herdr worktree remove` CLI options and workspace destruction order
- **Spec Section**: Section 4 (`herdr_task_close`, lines 132–137)
- **Problem**:
  The spec states:
  > `Stops tracking the task (final_status "closed" if it was not finished) and closes its workspace. With remove_worktree, run herdr worktree remove only when...`
  
  Two issues:
  1. `herdr worktree remove` CLI accepts only `--workspace <ID>`, `--force`, and `--trust-repository`. It does not accept path or branch arguments.
  2. If the workspace is closed first via `herdr workspace close <workspace_id>`, the workspace ceases to exist. Any subsequent `herdr worktree remove --workspace <workspace_id>` call fails with `workspace not found`.
- **Concrete Fix**:
  Update Section 4 to explicitly specify:
  1. Call `herdr worktree remove --workspace <record.workspace_id>` (with `--force` if requested) **before** closing the workspace.
  2. In `herdr`, removing a worktree workspace also removes the checkout and closes the workspace in one step. If `remove_worktree` succeeds, skip the separate `workspace close` call.

### 3. [BLOCKER] Section 4 — `herdr_task_close` destroys shared workspaces when placement was `pane_id`
- **Spec Section**: Section 4 (`herdr_task_close`, lines 133–134)
- **Problem**:
  The spec specifies that `herdr_task_close` unconditionally "closes its workspace".
  When a task was started with placement `pane_id` (an existing pane in a user's pre-existing workspace with other tabs/agents), closing the entire workspace destroys the user's ongoing work in unrelated panes.
- **Concrete Fix**:
  Only close the workspace if the task created a dedicated workspace (i.e. placement was `cwd` or `worktree`). If placement was `pane_id`, close only the pane (`herdr pane close <record.pane_id>`), or leave the pane open at its shell prompt without closing the enclosing workspace.

### 4. [BLOCKER] Section 3 — Premature task abort via "2 polls" rule and undefined `completion_seq` race condition
- **Spec Section**: Section 3 (`detectFinish`, lines 78–89)
- **Problem**:
  1. When an agent is newly started, `herdr agent get` does not have a `completion_seq` field (in herdr, `completion_seq` only appears after an agent transitions from `working` to `idle`). Thus, `record.baseline_completion_seq` is `undefined`.
  2. `detectFinish` specifies:
     `"idle_no_result": status ∈ {idle, done}, completion_seq > baseline_completion_seq (or the baseline is unknown and ≥ 2 polls have passed), and no fresh result file.`
  3. When an agent is dispatched, it starts in `idle`. If the agent takes more than 2 polls (e.g. 6 seconds with `poll_ms: 3000`) before transitioning to `working` (standard for LLMs starting up or reading prompts), `(baseline is unknown and >= 2 polls have passed)` evaluates to `true`. The task is prematurely aborted and marked `idle_no_result` before it even starts working!
  4. In JavaScript, `completion_seq > undefined` always evaluates to `false`. When the agent finally finishes work and gets `completion_seq = 1`, `1 > undefined` is `false`.
  5. Furthermore, `detectFinish` is defined as a pure function taking only `(snapshot, record, resultFile)`—it has no poll counter parameter.
- **Concrete Fix**:
  1. Remove the arbitrary ">= 2 polls" trigger from `detectFinish`.
  2. Track state transitions in `TaskRecord`: track `has_worked: boolean` (or `observed_working: boolean`) in the wait loop when `snapshot.agent_status === "working"`.
  3. For completion sequence: if `baseline_completion_seq !== undefined`, require `snapshot.completion_seq > baseline_completion_seq`. If `baseline_completion_seq === undefined`, a completion is indicated when `snapshot.completion_seq !== undefined` OR when `record.has_worked && snapshot.agent_status === "idle"`.
  4. Pass `observed_working` into `detectFinish` (or keep `detectFinish` strictly evaluating transition events). Never fail a task as `idle_no_result` unless the agent has actually worked and returned to idle, or until the overall `timeout_ms` expires.

### 5. [BLOCKER] Section 6 & Section 4 — MCP Progress notifications missing required plumbing and schema fields in `@modelcontextprotocol/sdk`
- **Spec Section**: Section 6 (lines 181–183) & Section 4
- **Problem**:
  1. In `src/server.ts`, tools are registered as:
     `async (args: Record<string, unknown>) => execTool(tool, args ?? {})`
     The second parameter `extra: RequestHandlerExtra` is discarded.
  2. In `src/tools/types.ts`, `ToolContext` only has `timeoutMs?: number`. There is no mechanism for `herdr_task_run` or `herdr_task_wait` to access `progressToken`, `sendNotification`, or `AbortSignal`.
  3. In `@modelcontextprotocol/sdk` v1.29.0 (`ProgressNotificationParamsSchema`), `params.progress` is a **required number** (`progress: z.ZodNumber`). Sending `{ progressToken, message }` without `progress` causes the SDK to throw a runtime Zod validation error.
  4. Long-running waits (up to 30 minutes) must listen to `extra.signal.aborted` so client disconnection or cancellation stops the polling loop immediately.
- **Concrete Fix**:
  1. In `src/server.ts`, pass `extra` into `execTool(tool, args, extra)`.
  2. Extend `ToolContext` in `src/tools/types.ts`:
     ```ts
     export interface ToolContext {
       timeoutMs?: number;
       signal?: AbortSignal;
       sendProgress?: (progress: number, message?: string, total?: number) => Promise<void>;
     }
     ```
  3. Implement `sendProgress` in `execTool`: if `extra._meta?.progressToken !== undefined`, call `extra.sendNotification({ method: "notifications/progress", params: { progressToken: extra._meta.progressToken, progress, total, message } })`.
  4. In `herdr_task_wait` and `herdr_task_run`, pass `progress: elapsedSeconds` (and `total: Math.round(timeoutMs / 1000)`), and abort the wait loop if `ctx.signal?.aborted` is true.

### 6. [BLOCKER] Section 7 & Section 4 — `fs.realpath` throws `ENOENT` on non-existent `result_path` before dispatch
- **Spec Section**: Section 7 (lines 189–190) & Section 4 (lines 107–109)
- **Problem**:
  Section 4 states: `Resolve it, reject paths that leave the cwd, then delete any stale file at that path before dispatch`.
  Section 7 states: `Result files and task_file are read only inside the agent cwd (checked after path.resolve and fs.realpath)`.
  Before dispatch, the result file does not exist yet (and any stale file was deleted). Calling `fs.realpath` on a non-existent path throws `ENOENT: no such file or directory` in Node.js.
- **Concrete Fix**:
  Split path validation into two distinct phases:
  1. **At dispatch time**: Validate that `path.resolve(cwd, result_path)` starts with `path.resolve(cwd) + path.sep` (or `path.relative(cwd, resolved)` does not start with `..` and is not absolute). Ensure the parent directory exists (`fs.mkdirSync(path.dirname(resolved), { recursive: true })`), and unlink any stale file (`fs.rmSync(resolved, { force: true })`).
  2. **At read time (after agent finishes)**: With the file now created on disk, call `fs.realpath` on both `cwd` and `result_path`. Verify `fs.realpathSync(result_path).startsWith(fs.realpathSync(cwd) + path.sep)`. Also check `fs.lstatSync(result_path).isFile()` and `!fs.lstatSync(result_path).isSymbolicLink()` to ensure it is not a symlink to outside the cwd or a FIFO/device.

## SHOULD Findings

### 7. [SHOULD] Section 3 — Fresh result file ignored when agent ends with `status: "blocked"`
- **Spec Section**: Section 3 (`detectFinish`, lines 82–84) & Section 1 (lines 44–45)
- **Problem**:
  The task prompt instructions state:
  > `When you finish, or if you are blocked and cannot continue, write <resultPath> as JSON with keys: status ("done" | "blocked" | "failed")...`
  
  However, `detectFinish` defines `"result"` as:
  `the result file exists, its mtime >= dispatched_at, and status ∈ {idle, done}.`
  If an agent writes a valid result file explaining that it is blocked, but its terminal status is `blocked` (e.g. at a permission prompt or dialog), Rule 1 (`result`) fails because `status` is not in `{idle, done}`. Rule 2 (`blocked`) matches instead.
  Consequently, Section 4 treats the task as `blocked` without a result, sets `view = agent read --source detection`, and completely ignores the result file written by the agent!
- **Concrete Fix**:
  If a fresh result file exists (`mtime >= dispatched_at`), evaluate `"result"` regardless of whether terminal status is `idle`, `done`, or `blocked`. When parsed, a result file containing `status: "blocked"` cleanly maps to `state: "blocked"` with both `result` and `view` preserved. Only treat the task as an uncompleted `blocked` state if there is no fresh result file.

### 8. [SHOULD] Section 4 — Ambiguity on `state` when `parseResult` fails
- **Spec Section**: Section 4 (lines 143–153)
- **Problem**:
  The spec defines valid output states as `"running" | "done" | "blocked" | "failed" | "timeout" | "missing_result"`, and defines `result_error?` for parse/schema failures.
  However, it never states what `state` is assigned when `parseResult` returns `{ ok: false, error, raw }`. Is it `"failed"`? Is it `"missing_result"`? Is `view` included?
- **Concrete Fix**:
  Explicitly specify: when a result file exists but `parseResult` fails (`ok: false`), set `state: "failed"`, populate `result_error: { error, raw }`, and include `view: last 40 compacted lines of visible`.

### 9. [SHOULD] Section 4 — Contradiction between plain text lines and JSON objects in `herdr_task_status`
- **Spec Section**: Section 4 (lines 128–130 vs lines 139–149)
- **Problem**:
  Line 129 states:
  > `One line per registered task: name · kind · running|<final_status> · elapsed · result_path.`
  
  Line 139 states:
  > `Output shape (all task tools): One JSON object per task: { name, state, ... }`
  
  An implementer cannot tell whether `herdr_task_status` returns plain text lines or JSON objects.
- **Concrete Fix**:
  Clarify that `herdr_task_status` returns formatted plain text lines (one per task), while `herdr_task_run` and `herdr_task_wait` return JSON objects/arrays matching the Section 4 JSON output shape.

### 10. [SHOULD] Section 4 — Undefined output shape for multi-task wait in `herdr_task_wait`
- **Spec Section**: Section 4 (lines 123–126 and lines 139–149)
- **Problem**:
  `herdr_task_wait` accepts `names: string[]` (1–16). Line 139 states: `One JSON object per task`. If multiple names are queried, does the tool return an array of JSON objects (`[ {...}, {...} ]`), or an object keyed by name? When `mode: "any"` is satisfied, does it return all queried tasks or only the one(s) that finished?
- **Concrete Fix**:
  Specify that `herdr_task_wait` returns a JSON array of task objects (`TaskOutput[]`). When `mode: "any"` is satisfied, return all queried tasks with their current states at the time of resolution.

### 11. [SHOULD] Section 1 & Section 8 — Prompt caching broken by footer structure
- **Spec Section**: Section 1 (lines 42–49) & Section 8 (`buildTaskPrompt`, lines 199–200)
- **Problem**:
  Line 49 states:
  > `Only <resultPath> varies, and it is the last part of the footer.`
  
  However, the quoted footer text has `<resultPath>` in its first sentence:
  > `When you finish, or if you are blocked and cannot continue, write <resultPath> as JSON with keys...`
  
  Because model prompt caching (e.g. Anthropic/OpenAI) relies on common token prefixes, varying `<resultPath>` in the first sentence invalidates prompt caching for the rest of the footer.
- **Concrete Fix**:
  Place `<resultPath>` at the very end of the footer text:
  > `When you finish, or if you are blocked and cannot continue, write the result file as JSON with keys: status ("done" | "blocked" | "failed"), summary (≤ 30 lines), files_changed, commits, tests {command, passed, notes}, questions, followups. Write the file with your file tool; do not print its contents. Then stop and wait.\nResult file path: <resultPath>`

### 12. [SHOULD] Section 2 — Cross-device rename failure on Linux with `os.tmpdir()`
- **Spec Section**: Section 2 (lines 66–68)
- **Problem**:
  Section 2 specifies saving `tasks.json` via an atomic rename: `write a temp file, then rename it`.
  If an implementer creates the temporary file in `/tmp` (e.g. using `os.tmpdir()`), `fs.rename` across filesystems fails on Linux with `EXDEV: cross-device link not permitted` because `/tmp` is frequently a `tmpfs` ramdisk while `$XDG_STATE_HOME` resides on the root/home disk.
- **Concrete Fix**:
  Specify that the temporary file must be written in the same directory as `tasks.json` (e.g. `path.join(stateDir, `tasks.json.tmp.${process.pid}.${Date.now()}`)`) before calling `fs.rename`.

### 13. [SHOULD] Section 5 — `herdr_agent_read` and `herdr_pane_read` currently use `buildArgs`
- **Spec Section**: Section 5 (lines 168–173)
- **Problem**:
  The spec adds `compact?: boolean`, `since_last?: boolean`, and `max_chars?: number` to `herdr_agent_read` and `herdr_pane_read`.
  Currently, both tools are implemented using `buildArgs` in `agent.ts` and `pane.ts`. `buildArgs` can only return CLI argv and cannot perform in-memory buffer tracking (`diffSinceLast`), output post-processing (`compactText`), or length capping.
- **Concrete Fix**:
  Note in Section 5 that `herdr_agent_read` and `herdr_pane_read` must be refactored from `buildArgs` to `run` handlers that invoke `runHerdr`, apply `compactText` and `diffSinceLast`, and store the last read per target/pane in an in-memory map.

---

### 14. [SHOULD] Section 4 — Git upstream check fails for new branches with no tracking upstream
- **Spec Section**: Section 4 (`herdr_task_close`, lines 135–136)
- **Problem**:
  The spec requires checking that `the branch has no commits missing from its upstream` before removing a worktree.
  When a worktree is created with a new branch (`herdr worktree create --branch feat-x`), the branch has no upstream tracking branch configured (`@{u}` does not exist). Running `git rev-list @{u}..HEAD` fails with `fatal: no upstream configured for branch 'feat-x'`. Without handling this case, all newly created worktrees will be refused for removal unless `force: true` is passed.
- **Concrete Fix**:
  Specify the upstream check fallback:
  1. Check if upstream tracking branch exists (`git rev-parse --verify --quiet @{u}`).
  2. If an upstream exists, check `git rev-list @{u}..HEAD`.
  3. If no upstream exists, check against the base ref (from `worktree.base` or default remote `origin/main` / `origin/HEAD`). If unpushed commits exist relative to the base ref, require `force: true`.

### 15. [SHOULD] Section 1 — Rigid `tests` schema fails on common LLM array responses
- **Spec Section**: Section 1 (`resultSchema`, lines 36)
- **Problem**:
  The spec defines `tests?: { command: string, passed: boolean, notes?: string }`.
  LLMs frequently output an array of test commands (e.g. `tests: [{ command: "npm test", passed: true }]`) or multiple test results. Validating `tests` strictly as a single object causes schema validation failure on valid builder outputs.
- **Concrete Fix**:
  Define `tests` in Zod as:
  ```ts
  tests: z.union([
    testItemSchema,
    z.array(testItemSchema)
  ]).optional()
  ```

## NIT Findings

### 16. [NIT] Section 2 — Over-engineered `ledger.jsonl` without consumers
- **Spec Section**: Section 2 (lines 69–71)
- **Problem**:
  The spec defines an append-only `ledger.jsonl`. No MCP tool reads, queries, aggregates, or prunes this file, and Section 10 explicitly places token and cost accounting out of scope. Over time, `ledger.jsonl` grows unbounded without rotation.
- **Concrete Fix**:
  Either cut `ledger.jsonl` from the 0.3.0 scope (relying on `tasks.json` which already has a 7-day retention policy), or document it as an optional append-only audit log with line rotation.

---

### 17. [NIT] Section 1 — Strict line and character limits in `summary` schema
- **Spec Section**: Section 1 (`resultSchema`, line 33)
- **Problem**:
  `summary` has comments `max 3000 chars, ≤ 30 lines`. If implemented as strict Zod schema constraints (`.max(3000)` and `.refine(s => s.split('\n').length <= 30)`), an LLM returning 31 lines or 3050 characters will fail the entire task contract as invalid JSON.
- **Concrete Fix**:
  Validate `summary: z.string()` in the schema. Enforce the 30-line and 3000-char limits during post-processing / compaction in `compact.ts` rather than failing contract validation.

---

### 18. [NIT] Section 4 — Auto-create parent directory for default `result_path`
- **Spec Section**: Section 4 (lines 107–109)
- **Problem**:
  The default `result_path` is `.agent/out/<name>.json`. In a fresh workspace or worktree, the `.agent/out/` directory does not exist. Agents attempting to create files using standard tools (like `fs.writeFile`) will fail if the parent directory does not exist.
- **Concrete Fix**:
  Specify that `herdr_task_run` ensures `path.dirname(resolvedResultPath)` is created with `fs.mkdirSync(dir, { recursive: true })` prior to agent prompt dispatch.

---

### 19. [NIT] Section 5 — Box-drawing regex colliding with markdown tables
- **Spec Section**: Section 5 (`compactText`, lines 161–162)
- **Problem**:
  The spec instructs dropping `lines made only of box-drawing, spinner or rule characters`. If the regex is too broad, it could strip markdown table separators or ASCII diagrams.
- **Concrete Fix**:
  Specify the exact regex for dropping decorative borders:
  `^[\s─━│┃┌┐└┘├┤┬┴┼═║╒╓╔╕╖╗╘╙╚╛╜╝╞╟╠╡╢╣╤╥╦╧╨╩╪╫╬⠋-◒-]+$` without stripping lines containing alphanumeric characters or standard markdown column pipes (`|`).

---

### 20. [NIT] Section 4 — JSON truncation without string parsing corruption
- **Spec Section**: Section 4 (lines 154) & Section 8 (lines 207)
- **Problem**:
  Section 4 specifies: `The whole response is cut to max_chars, cutting view first, then summary`. Section 8 test requires: `a 10 000-char view is cut first, and the JSON still parses`.
  Truncating a serialized JSON string at `max_chars` produces invalid JSON with unclosed quotes and brackets.
- **Concrete Fix**:
  Clarify that character budgeting must be applied to the string properties (`view`, then `result.summary`) before calling `JSON.stringify`, guaranteeing that the final output is always valid JSON.

---

### 21. [NIT] Section 7 — Ambiguity regarding `task_file` size check
- **Spec Section**: Section 7 (lines 189–190) vs Section 4 (lines 105–106)
- **Problem**:
  Section 7 states: `Result files and task_file are read only inside the agent cwd ... max 64 KB`. But Section 4 states: `With task_file, the prompt is "Read <task_file> and carry it out." plus the footer`. It is ambiguous whether the MCP server is supposed to read and inline `task_file`, or merely validate its existence and size on disk before prompting.
- **Concrete Fix**:
  Clarify that `herdr_task_run` validates that `task_file` exists inside `cwd`, is a regular file, and is `<= 64 KB` before dispatching the prompt, but does not inline its contents into the prompt string.
