# herdr-mesh 0.3.0 — task tools and compact reads

Target: herdr **0.9.5** (unchanged). Version bump to **0.3.0** in `package.json` and `src/server.ts`.
Base branch: `fix/herdr-0.9.5-support` (0.2.0). Work branch: `feat/0.3.0-task-tools`.
`dist/` is committed: rebuild and commit it.

## Why

The orchestrating agent (Claude Code) spends most of its tokens babysitting builders:
reading 80–200 lines of TUI screen per check, re-reading after every fix round, and
being woken by polling monitors. 0.3.0 moves the waiting and the screen-watching into
the MCP server, where it costs no model tokens, and returns only a small structured
result the builder writes itself.

Rules for every new tool:
- Return compact text: one JSON object, at most `max_chars` (default 4000) characters.
  Never return a full pane buffer unless the caller asks for it.
- Waiting happens inside the server by polling herdr (no model tokens).
- No new runtime dependencies. Node 22 built-ins only (`node:fs`, `node:path`, `node:os`,
  `node:child_process`).
- Additive only: no existing tool changes its inputs or default behavior, except the new
  optional inputs listed under "Compact reads".

## 1. Result contract

A task ends when the builder writes a **result file** (JSON) and goes idle.

New file `src/task/contract.ts`:
- `resultSchema` (zod):
  ```
  {
    status: "done" | "blocked" | "failed",
    summary: string,                 // plain z.string(); the 30-line / 3000-char limit is
                                     // applied when output is built (section 4), never in the schema
    files_changed?: string[],
    commits?: string[],              // short SHAs
    tests?: Test | Test[],           // Test = { command: string, passed: boolean, notes?: string }
    questions?: string[],            // things the orchestrator must decide
    followups?: string[]
  }
  ```
  Unknown keys are kept (`.passthrough()`), so callers can extend it.
- `buildTaskPrompt(task: string, resultPath: string): string` — returns `task`, a blank line,
  then a **fixed footer** (identical text every time), then one final line with the path:
  > When you finish, or if you are blocked and cannot continue, write the result file as JSON
  > with keys: status ("done" | "blocked" | "failed"), summary (≤ 30 lines), files_changed,
  > commits, tests {command, passed, notes}, questions, followups. Write the file with your
  > file tool; do not print its contents. Then stop and wait.
  > Result file path: `<resultPath>`

  Only the last line varies.
- `parseResult(text: string): { ok: true, result } | { ok: false, error: string, raw: string }`
  — JSON parse + schema check; `raw` is truncated to 2000 chars.

## 2. Task registry

New file `src/task/registry.ts`. One record per task, keyed by agent name:
```
{
  name, kind, pane_id, workspace_id, cwd,
  placement: "cwd" | "worktree" | "pane_id",
  created?: { kind: "workspace" | "tab" | "pane", id: string },  // what task_run created, if anything
  result_path,            // absolute
  worktree?: { path, branch, base? },
  dispatched_at,          // ISO
  baseline_completion_seq?: number,   // absent until the agent has completed once
  observed_working: boolean,          // set true the first time a poll sees "working"
  finished_at?, final_status?   // "done" | "blocked" | "failed" | "timeout" | "missing_result" | "closed"
}
```
- In memory, persisted on every change to `$XDG_STATE_HOME/herdr-mesh/tasks.json`
  (fallback `~/.local/state/herdr-mesh/tasks.json`) with an atomic write: write
  `tasks.json.tmp.<pid>.<ms>` **in the same directory**, then rename it (never `os.tmpdir()`,
  which can be another filesystem). The registry survives MCP server restarts.
- On finish, append one line to `ledger.jsonl` in the same directory:
  `{name, kind, args, started, finished, elapsed_ms, final_status, files_changed_count}`.
  It is used for per-task cost/time tracking; it holds no prompt text and no output.
  When it passes 1 MB, rename it to `ledger.jsonl.1` (replacing any old one) before appending.
- Records older than 7 days are dropped on load.

## 3. Finish detection

Pure function in `src/task/detect.ts` (unit-tested without herdr):
```
detectFinish(snapshot: { agent_status: string, completion_seq?: number },
             record: TaskRecord, resultFile: { exists: boolean, mtimeMs?: number })
  → "running" | "result" | "blocked" | "idle_no_result"
```
The wait loop sets `record.observed_working = true` (and persists it) before calling
`detectFinish` whenever a poll sees `agent_status === "working"`. Then, in this order:
1. `"result"`: the result file exists and its mtime ≥ `dispatched_at` — **whatever** the
   agent status is (an agent may write a "blocked" result and then sit at a dialog).
2. `"blocked"`: `agent_status === "blocked"` (usually a permission dialog).
3. `"idle_no_result"`: status ∈ {idle, done} and the agent has completed a turn since dispatch:
   - baseline defined → `completion_seq !== undefined && completion_seq > baseline`;
   - baseline undefined → `completion_seq !== undefined || record.observed_working`.
4. Otherwise `"running"`. No poll counting: an agent that never starts simply runs into
   `timeout_ms`.

`completion_seq` is absent from `agent get` until the agent has completed once (verified on
0.9.5: a fresh agent has only `state_change_seq`), hence the undefined handling. Never compare
a number with `undefined`.

## 4. New tools (`src/tools/task.ts`, registered first in `server.ts`)

### `herdr_task_run`
Start an agent, hand it a task, optionally wait, and return only the compact result.

Inputs:
- `name` (agent-name regex), `kind` (AGENT_KINDS), `args?` — same as `herdr_agent_start`.
- Placement, exactly one of:
  - `cwd` — new workspace in this directory (current `agent_start` default path);
  - `worktree: { repo: string, branch: string, base?: string, path?: string }` — runs
    `herdr worktree create --cwd <repo> --branch <branch> [--base] [--path] --label <name> --no-focus`.
    Its result is `{ type: "worktree_created", workspace: WorkspaceInfo, worktree: WorktreeInfo }`
    with **no pane id**: take `result.workspace.workspace_id`, then
    `herdr pane list --workspace <id>` and use its only pane. The agent cwd is
    `result.worktree.path`. `created = { kind: "workspace", id }`;
  - `pane_id` — an existing shell pane. `created` stays unset.
- `task` (string) **or** `task_file` (path relative to the agent cwd). With `task_file`,
  the server checks that it is a regular file inside the cwd and ≤ 64 KB, but does **not**
  inline it: the prompt is `Read <task_file> and carry it out.` plus the footer.
- `result_path?` — default `.agent/out/<name>.json`, relative to the agent cwd.
  At dispatch: `path.resolve(cwd, result_path)`; reject it if `path.relative(cwd, resolved)`
  starts with `..` or is absolute; `mkdir -p` its parent; `rm -f` any stale file. (No
  `realpath` here — the file does not exist yet. The realpath check happens at read time,
  section 7.)
- `wait?` (boolean, default `true`), `timeout_ms?` (default 600000, max 1800000),
  `poll_ms?` (default 3000, min 1000).
- `max_chars?` (default 4000).

Steps: reuse the placement + `startAgent` + cleanup code from `herdr_agent_start` (extract
it into a shared helper rather than copying it). Read `agent get` for the baseline
`completion_seq`. Register the task. Send `agent prompt <name> <buildTaskPrompt(...)>`.
Then wait as in `herdr_task_wait`, unless `wait` is false.

If `agent start` returns `agent_not_ready` (blocked at startup, e.g. a trust dialog),
register the task as dispatched=false and return the blocked view (below) without prompting.

### `herdr_task_wait`
Inputs: `names: string[]` (1–16), `mode?: "any" | "all"` (default `any`), `timeout_ms?`,
`poll_ms?`, `max_chars?`.
Poll every `poll_ms`: one `herdr agent list` call (not one call per agent), plus a stat of
each pending result file. Return when the mode is satisfied or on timeout. Returns a JSON
**array** with one output object for **every** name asked for (finished or still `running`).
Unknown names come back as `{ name, state: "failed", result_error: "unknown task" }`.

### `herdr_task_status`
No inputs except optional `names`. No waiting. Returns **plain text**, one line per registered
task: `name · kind · running|<final_status> · elapsed · result_path`.

### `herdr_task_close`
Inputs: `name`, `remove_worktree?` (default false), `force?` (default false).
Stops tracking the task (final_status "closed" if it was not finished). Then:
- `placement: "pane_id"` → close **nothing** (the pane and workspace belong to the caller).
- `remove_worktree: true` (worktree placement only) → refuse unless `force`, when either
  `git -C <path> status --porcelain` is non-empty or `git -C <path> rev-list --count HEAD --not --remotes`
  is not `0` (commits that exist on no remote; this also covers branches with no upstream).
  Otherwise run `herdr worktree remove --workspace <workspace_id> [--force]` **before** anything
  else; it removes the checkout and closes the workspace, so skip the close below.
- Else → close what `created` names (`workspace close` / `tab close` / `pane close`).
Never deletes branches.

### Output shape (`herdr_task_run`, `herdr_task_wait`)
One JSON object per task (`task_run` returns one object, `task_wait` an array):
```
{
  name, state: "running" | "done" | "blocked" | "failed" | "timeout" | "missing_result",
  elapsed_ms, cwd, result_path,
  result?,          // parsed result file
  result_error?,    // parse/schema error + truncated raw text
  view?             // compact screen text, only for blocked / missing_result / timeout
}
```
- `blocked`: `view` = `agent read --source detection` (or `visible` if detection is empty),
  compacted, max 40 lines, so the caller sees only the dialog.
- `missing_result` / `timeout`: `view` = last 40 compacted lines of `visible`.
- A result file with `status: "blocked" | "failed"` maps to that state; with `blocked`, `view`
  is added as well.
- A result file that exists but fails `parseResult` → `state: "failed"`, `result_error:
  { error, raw }`, plus the `missing_result` view.
- `result.summary` is cut to its last 30 lines / 3000 chars here.
- Size budget: trim the string fields **before** `JSON.stringify` (first `view`, then
  `result.summary`, then `result_error.raw`) until the serialized output is ≤ `max_chars`.
  Never cut the serialized JSON; the output must always parse.

## 5. Compact reads

New file `src/compact.ts`, pure functions:
- `compactText(text, { maxLines?, maxChars? })`:
  - strip ANSI escapes and trailing whitespace;
  - drop lines matching `/^[\s─-╿⠀-⣿◐◓◑◒●○▸▪…]*$/u` that are not empty
    (Unicode box-drawing, braille spinners, TUI bullets only). ASCII is never dropped, so
    markdown tables, `---` rules and `|` pipes survive;
  - collapse runs of blank lines to one, and runs of identical consecutive lines to one plus `(×N)`;
  - keep the **last** `maxLines`, then cut to `maxChars` from the start.
- `diffSinceLast(prev: string, next: string): string` — returns the lines of `next` after
  the longest overlap between the end of `prev` and the start of `next`; returns `next` whole
  when there is no overlap.

New optional inputs on `herdr_agent_read`, `herdr_pane_read` and `herdr_handoff`:
- `compact?: boolean` (default false) — run `compactText` on the output.
- `since_last?: boolean` (default false) — keep the last read per target in memory and return
  only `diffSinceLast`. The first call returns the full (compacted) read.
- `max_chars?: number`.
Defaults are unchanged, so existing callers see no difference. `herdr_agent_read` and
`herdr_pane_read` are `buildArgs` tools today; convert them to `run` handlers (keeping the exact
argv, which `test/args.test.ts` must still assert via an exported argv builder). The last-read
map is keyed by resolved pane id and lives in memory only.

## 6. Long-running calls

- Blocking task tools may run up to 30 minutes. Document in the README that MCP clients need a
  tool timeout above the requested `timeout_ms` (Claude Code: `MCP_TOOL_TIMEOUT`; OpenCode:
  the per-server `timeout`), and recommend `wait: false` + repeated `herdr_task_wait` calls
  with `timeout_ms ≤ 600000` when unsure.
- Plumbing (SDK 1.29.0): `server.ts` passes the handler's second argument (`extra`) to
  `execTool(tool, args, extra)`. `ToolContext` gains
  `signal?: AbortSignal` and `sendProgress?: (progress: number, total?: number, message?: string) => Promise<void>`.
  `execTool` sets `sendProgress` only when `extra._meta?.progressToken !== undefined`; it calls
  `extra.sendNotification({ method: "notifications/progress", params: { progressToken, progress, total, message } })`
  — `progress` is **required** by the SDK schema.
- While waiting, call `sendProgress(elapsedSeconds, timeoutSeconds, "<name>: <status>")` every 30 s
  (errors ignored), so clients that reset timeouts on progress keep the call alive.
- Check `ctx.signal?.aborted` on every poll; on abort stop polling and return the current
  state (the task keeps running and stays in the registry).
- `execTool`'s subprocess timeout scaling does not apply to the wait loop itself; each herdr
  call inside the loop keeps the default 30 s timeout.

## 7. Security limits

- At read time, result files and `task_file` must pass: `fs.lstat` says regular file (not a
  symlink, FIFO or device), size ≤ 64 KB, and `realpath(file)` starts with `realpath(cwd) + path.sep`.
  Otherwise treat the file as missing and say why in `result_error`.
- The server never auto-answers permission dialogs. A blocked agent is reported, not approved.
- The registry and ledger store no prompt text, no screen output and no environment variables.
- Remote machines (`herdr --machine`) are out of scope: result files are read from the local
  filesystem. Document this.

## 8. Tests

`test/task.test.ts` (node:test via tsx, no herdr needed):
- `buildTaskPrompt`: for two different tasks and paths, everything after the task text except
  the last line is byte-identical.
- `parseResult`: valid result; missing `status`; non-JSON; extra keys kept; raw truncated to 2000;
  `tests` as an object and as an array; a 40-line summary still parses.
- `detectFinish`: every branch, including: stale result mtime < dispatched_at; a fresh result
  while status is `blocked` → `"result"`; a stale result while blocked → `"blocked"`; idle with
  undefined baseline and undefined `completion_seq` and `observed_working` false → `"running"`;
  undefined baseline + `observed_working` → `"idle_no_result"`.
- `herdr_task_close` decision (pure helper): `pane_id` placement closes nothing; unpushed
  commits or a dirty tree refuse without `force`.
- Registry: persists and reloads (temp `XDG_STATE_HOME`), drops records older than 7 days,
  ledger line has no prompt text.
- Result path: `../x.json` and an absolute path outside the cwd are rejected.
- Output cutting: a 10 000-char view is cut first, and the JSON still parses.

`test/compact.test.ts`: ANSI stripped; spinner/box lines dropped; `(×N)` collapsing; `maxLines`
keeps the tail; `diffSinceLast` with full, partial and no overlap.

`test/args.test.ts`: argv for `worktree create` and `worktree remove` placement.

`scripts/smoke.mjs`: with `SMOKE_AGENT=<kind>` set, also run `herdr_task_run` in a scratch
workspace with the task "Write the result file with status done and summary 'smoke'", check
`state === "done"`, then `herdr_task_close`. Without it, skip (no model cost by default).

`npm run build && npm test` must pass; `node scripts/smoke.mjs` must pass against the live
herdr server.
